# IriX Node 架构设计

这份设计把 IriX Node 视为一个本地控制平面：客户端通过 HTTP API 管理实例、文件、任务、账户、集群和加密保险库；守护进程负责把请求转换为受控的进程操作，并把状态安全地写入本地或外部存储。

采用**模块化单体**：继续交付一个跨平台 Go 二进制，以文件和组件划分职责。单台节点的进程控制、文件操作和保险库共享本地状态，部署为多个服务会增加认证、状态同步和故障恢复成本。当前先落实组合根、HTTP 入口和生命周期边界，为业务模块后续拆分提供稳定基础。

## 设计目标

- **边界清晰**：传输层只负责协议和中间件，业务模块通过 `Daemon` 访问实例与基础设施。
- **状态安全**：实例配置经过内存快照、原子写入和优雅关停兜底；Redis 只做缓存，SQL/文件存储才是权威数据源。
- **可控生命周期**：HTTP、周期任务、实例/FRP 子进程和数据库都有明确的启动/关停顺序；长任务执行器的取消策略列入后续演进。
- **跨平台稳定**：进程、系统信息、文件描述符和权限收敛继续通过构建标签隔离，核心编排不依赖操作系统细节。
- **渐进演进**：在不改变现有 MCSManager 风格 API 的前提下，可以逐步把大模块拆为独立服务或适配器。

## 分层与依赖方向

| 层 | 当前实现 | 责任 | 依赖规则 |
| --- | --- | --- | --- |
| 组合根 | `main.go` 的 `runNode` | 解析配置、创建 `Daemon`、初始化存储和 TLS、接收信号 | 可以依赖所有模块；业务规则留在用例方法中 |
| 生命周期 | `app_runtime.go`、`daemon_lifecycle.go` | 服务运行、取消、登记/排空、周期任务、进程启动门禁 | 管理资源的生存期，不解析业务参数 |
| 传输层 | `http_server.go`、`instance.go`、`cors.go`、`audit.go`、`console_ws.go` | HTTP/WS 组装、路由、认证/权限、CORS、请求体限制、统一响应 | 调用现有 `Daemon` 用例方法 |
| 应用模块 | `files.go`、`backup.go`、`cluster.go`、`container.go`、`vault_handlers.go`、`accounts_handlers.go` | 编排一个用例，校验输入，映射错误和异步任务 | 通过 `Daemon` 访问领域和适配器 |
| 核心模型 | `daemon.go`、`instance.go` 的实例用例、`process.go`、`jobs.go` | 实例状态、进程状态、任务状态、并发边界、状态迁移 | 当前仍与 HTTP 方法共用包；逐步减少跨模块字段访问 |
| 基础设施适配器 | `accounts*.go`、`vault_store.go`、`logger.go`、`sysinfo_*.go`、`process_*.go` | SQL/Redis、加密对象、日志、平台能力 | 只实现领域需要的能力 |
| 持久化边界 | `instances.json`、`accounts.db`、`vault/`、`logs/`、外部 SQL/Redis | 保存配置、账户、密文对象、审计与实例日志 | 不直接参与请求路由 |

目标依赖方向为“入口 → 传输 → 应用 → 核心模型 → 适配器”。当前所有代码仍在 `package main`，这是一份组件职责约束，并不是已由 Go 包系统强制执行的独立分层。`instance.go` 同时含路由和实例用例，部分基础设施文件也含处理器；本次没有把现有模块包装成空接口。异步任务继续通过任务表报告进度。

## 启动与资源所有权

`main` 只处理最终错误、退出码和全局日志排空；`runNode` 合并配置、初始化账户/保险库、加载实例、准备认证/TLS/监听器。初始化失败通过返回错误触发已创建资源的清理。保险库迁移标记先于实例列表加载，避免启动时错误地选择明文存储路径。

`NewDaemon`、`newTaskStore`、`newVaultState` 和传输票据/保险库存储只分配状态，不启动永久循环。`nodeRuntime.run` 接管监听器后启动配置落盘、任务与传输票据过期清理、保险库会话与索引清理以及可选负载调谐；指标循环在首次查询时登记。节点级周期任务统一受可取消的 `backgroundWorkers` 管理。自动启动实例被移至运行时，初始化失败时不会提前创建子进程。

信号取消与 `Serve` 异常返回都执行同一清理路径；不再在服务错误路径直接 `log.Fatal` 或等待一个不会出现的信号。

## 一次请求的生命周期

1. `http.Server` 接收连接，连接层只记录 Accept 错误，避免日志拖慢 accept 循环。
2. 请求门禁登记在途请求，再依次执行审计、CORS、保险库门禁和 API 请求体限制。登记涵盖处理器返回后的审计写入，不包装 `ResponseWriter`，保留 WebSocket 所需能力。
3. `auth` 先解析固定 API key/配对码或账户会话，再做端点权限判定。
4. 处理器完成参数校验后调用 `Daemon` 的用例方法。实例列表由 `Daemon.mu` 保护，实例字段由 `Instance.mu` 保护。
5. 长任务立即返回任务 ID，由 `taskStore`/`jobStore` 保存进度；文件下载和上传通过短期票据切换到直连通道。
6. 响应统一使用 `{status, data, time}`，错误同时返回真实 HTTP 状态码，便于网关和监控识别失败。

## 持久化与一致性

实例增删改采用“脏标记 + 防抖批量写入”：请求路径修改内存并设置 `dirty`，后台循环在窗口内执行一次完整序列化、`fsync` 和 `rename`。正常磁盘条件下异常退出可能丢失最近一个窗口内的变更；写盘持续失败时未保存变更可能更久。写入失败保留脏标记；加密索引刷新失败也会向上传递，不再报告保存成功。

`app_runtime.go` 中的 `nodeRuntime` 是唯一的运行时关停编排器，顺序固定为：

1. 封闭请求和进程启动入口，关闭 HTTP 已劫持的控制台连接；
2. 关闭 HTTP 监听器并排空在途请求，超过 15 秒则强制关闭活动连接；
3. 等待已登记的处理器与启动操作结束，停止并等待配置落盘和其它周期任务；
4. 刷入脏配置，再停止实例和 FRP 子进程、回收加密文件树并保存最终状态，等待退出监听结束；
5. 关闭 SQL/Redis，在保险库已解锁时刷新索引；最后排空审计与全局日志。

编排器使用 `sync.Once`，并发/重复触发关停只执行一次并共享结果。HTTP、写盘、停止实例、FRP、数据库和保险库刷新错误合并返回，其余清理继续执行。`StartAutoSave`/`StopAutoSave` 的启动与封闭串行化，停止方法等待进行中的写入完成后返回。

15 秒是 HTTP 网络排空预算，实例停止另有 30 秒预算，整次关停不是固定 15 秒。强制关闭连接会取消请求上下文，但不能强制终止忽略取消的 Go 处理器；为避免关闭仍被使用的数据库，处理器退出等待可能延长关停。现有备份、JDK 下载、集群传输及容器长任务仍沿用原执行机制，尚未统一取消/恢复，这一点不由本次周期任务管理器解决。

## 并发约束

- 读取 `Daemon.Instances` 必须持有 `Daemon.mu`；拿到实例指针后，读取 `Status`、`Proc` 或 `Config` 必须持有 `Instance.mu`。
- 不在持有 `Daemon.mu` 时执行文件 I/O、进程停止、加密回收或网络请求。
- `saveMu` 必须先于 `Daemon.mu` 获取，避免持久化与请求路径形成锁顺序反转。
- 日志、任务和缓存使用有界队列或过期策略；慢磁盘、Redis 故障和日志风暴不能把背压传递给实例进程。
- 关停时先解除实例进程引用，再等待停止；自动重启逻辑不会把主动关停误判成崩溃。

本次实现同时修复了 `StopAll` 中读取 `Instance.Config.VaultFiles` 的锁外访问：该字段现在与停止命令、工作目录一起在 `Instance.mu` 内复制，再用于关停后的加密回收。

## 故障与恢复策略

- `instances.json` 解析失败时备份损坏文件并以空列表启动，避免节点完全不可用。
- Redis 不可用时鉴权和权限读取自动回退 SQL；Redis 恢复后重新启用热缓存。
- 审计和实例日志采用异步、有界队列；队列满时统计丢弃量，不阻塞业务和实例 stdout。
- 保险库启用时强制 TLS，数据面由 `vaultGate` 统一拦截；解锁会话超时后自动锁定。
- 集群传输在连接前校验协议、目标 IP 和允许网段，失败只标记任务，不影响本节点其它实例。

## 交付与后续演进

本次落实组合根错误清理、HTTP 处理链组装、幂等运行时关停、在途请求与 WebSocket 排空、进程启动门禁、可取消周期任务及配置刷盘等待。回归用例覆盖服务异常退出、数据库关闭顺序、网络排空超时、配置失败后继续清理、并发关停和进行中的写盘等待。

后续可按实际需求继续拆分：

1. 为文件、集群、账户和保险库定义窄接口，把处理器从 `Daemon` 具体字段迁移到应用服务；
2. 在出现第二种实例存储需求时引入 `InstanceRepository`，保留 JSON/保险库实现；
3. 将任务执行器统一为带 `context.Context` 的 worker pool，支持节点关停时取消排队任务；
4. 在端点契约需要演进时引入 API 版本，将响应结构与内部模型解耦。

这些步骤都可以独立发布；本次生命周期边界不会改变现有端点契约和数据目录格式。
